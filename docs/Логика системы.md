# Логика системы

Дата: 10 октября 2026 года.

Последнее решение: ручное включение/выключение с пульта через меню ТВ.
Автоматический запуск по HDMI/приложению и определение русского языка отменены.
Уточнение: Bergamot остаётся предварительным переводчиком, Google выполняет
окончательный перевод только после трёх подтверждений исходного текста.
OFF прекращает обмен OSD с Orange; Orange выгружает модели по своему таймеру
после пяти минут отсутствия активности.

Это целевая спецификация обсуждаемого обновления, а не утверждение, что вся
описанная цепочка уже установлена. Состояние реализации и открытые решения
перечислены в конце. Детектор, модели и правила образования кропов не меняем
ради ускорения без отдельной проверки качества.

## 0. Ручное управление переводом

Пользователь включает/выключает перевод кнопкой «Перевод» в TV-меню приложения,
используя OK на пульте. Дополнительно тот же переключатель доступен в PIN-меню
телефона. Единственный флаг — `translationEnabled` в существующем файле настроек
OSD на ТВ. По умолчанию выключен. ON действует только в текущем сеансе бодрствования:
при каждом старте контроллера сохранённый ON сбрасывается в OFF, оформление
сохраняется. После сна/выключения и пробуждения ТВ также остаёмся OFF, до нового
ручного включения. Сохранённый файл — текущее состояние, не разрешение на будущий запуск.

HDMI, приложения, русский/английский текст и чёрный экран не включают перевод
автоматически. Старые поля списков источников и языка сохранены для совместимости
server API, но новый контроллер их не использует для допуска.

- ON: разрешаем обработку текущего оригинального экрана обычными тремя OCR.
- OFF: прекращаем рабочий обмен OSD с Orange, запрещаем новые кадры,
  инвалидируем поздние ответы и убираем переводные
  плашки. Принятое задание может безопасно завершиться; отмена уже отправленного
  HTTP-запроса не означает отмену расхода символов Google.
- Смена источника при ON меняет epoch, чтобы ответы прежнего экрана не попадали
  на новый; сам ручной флаг не выключается и не включается из-за HDMI/приложения.
- Собственные меню/OSD не переводим. Открытие наших настроек временно приостанавливает
  задания, но не меняет ON и не означает полный сон с выгрузкой моделей.
- При недоступном контроллере/невалидном состоянии новые задания запрещены.

Определять foreground всё ещё нужно для идентичности сессии и отсеивания
собственного OSD, а не для автоматического выбора, где запустить перевод.
Контроллер работает в фоне после закрытия страницы настроек.

### 0.1. Сон OSD

Ручной OFF / сон OSD означает отсутствие его рабочего обмена с Orange, а не
немедленную команду убить сервисы. Новые кадры/переводы не отправляем; фоновые
опросы Orange прекращаем. Ранее принятые задания могут завершиться, но их
ответы не разрешают показ на выключенном OSD.

На Orange нужен постоянно доступный лёгкий supervisor: он фиксирует последнюю
активность OSD монотонными часами Orange. Через 300 секунд без активности
останавливает тяжёлые модули/работники/службы этой цепочки и освобождает модели,
RKNN contexts и буферы. Выгрузка выполняется безопасно: активная принятая работа
не уничтожается посередине; после её завершения проверяем истёкший idle deadline.
Другие сервисы Orange и обычный захват PicCap не останавливаем.

Supervisor, входной endpoint и TV web-сервер меню остаются доступны. Иначе после
остановки всех слушателей некому принять новый ON/кадр и разбудить работников.
ON до истечения пяти минут использует загруженные модели; после выгрузки нужен
прогрев. Orange запрашивает кадр только после готовности работников; сам этот
запрос заменяет отдельное сообщение READY. До запроса кадра для отправки нет.
Старые пакеты не ставим в очередь
на время загрузки. Кэш, счётчик Google, ключ и настройки не сбрасываем.

**Важная граница:** существующий controller опрашивает `/api/settings` каждые
2 секунды, а UI бюджета — Orange каждые 3 секунды. В новом OFF эти автоматические
запросы тоже нужно прекратить; иначе «пять минут никто не обращается» не наступят.
При OFF меню показывает последний снимок счётчика с отметкой времени, а не
заявляет, что расход живой. Явные операции настройки ключа/provider отделяем от
рабочей активности, чтобы они не запускали OCR и не удерживали тяжёлые модели;
такое разделение ещё нужно реализовать. Проверки health/посторонние HTTP-запросы
не должны продлевать рабочий idle deadline.

Остановка фоновых опросов и локальные snapshots реализованы в коде пакета 0.1.6,
но ещё не установлены на ТВ. Протокол supervisor и выгрузка по таймеру пока не
реализованы. Это новое правило заменяет немедленную выгрузку на ручном OFF.

Чёрный экран и отсутствие текста при ON не выгружают и не перезапускают три
OCR-работника. Русского языкового работника в новой целевой цепочке нет.

### 0.2. Пульт: подтверждённый путь и горячая кнопка

Реализован TV-экран: открыть Game Translator с пульта, выбрать кнопку переключателя,
нажать OK и вернуться к игре кнопкой «Назад». Код использует обычные события
пульта открытого приложения, не глобальный перехват клавиш поверх HDMI.
Обычное фоновое webOS-приложение не получает такие keypress события:
[ответ LG](https://forum.webostv.developer.lge.com/t/how-to-catch-keypress-on-remote-control-in-the-background-app-or-in-the-service/5383).

Горячую кнопку без открытия меню можно исследовать отдельно на нашем rooted ТВ.
Пока нет доказанного пути получения событий, такую привязку не обещаем и не
перехватываем Power/громкость/другие системные кнопки. Установка и физическая
проверка нового переключателя ожидают доступности ТВ.

### 0.3. Полное выключение, standby и пробуждение ТВ

Перезапуск процесса и сон телевизора — разные события. Если процесс остаётся
живым в standby, одного сброса при запуске недостаточно. `tv-power.js` использует
найденный в AmbiSun URI `tvpower/power/getPowerState`, поля `state`/`powerState`
и отдельный постоянный `luna-send -i -f` subscriber. Поток JSON разбирается с
ограничением размера. Формат CLI описан в
[luna-send Usage Guide](https://www.webosose.org/docs/tools/commands/luna-send/);
это не доказательство доступности приватного tvpower API на конкретном G5.

Распознанные On/Active разрешают ручное включение. Standby/Suspend/Off,
системный Screen Saver/ScreenOff и потеря подписки сбрасывают флаг и допуск в OFF,
останавливают автоопросы Orange и блокируют старые ответы. Пробуждение только
разрешает новое нажатие ON, но само перевод не включает. Начальное/неизвестное
питание и неподтверждённая подписка запрещают ON из TV-меню и с телефона.
Смена состояния питания также инвалидирует revision управляющих команд,
даже если флаг уже был OFF. Старый запрос ON до сна не применяется после
пробуждения. Revision нового экземпляра контроллера имеет отдельный случайный
seed; команда прежнего экземпляра отклоняется. Телефон не повторяет ON
автоматически после сетевой ошибки или конфликта: нужно новое ручное нажатие.
Неизвестные значения не объявляются включённым ТВ. На ошибке подписка повторяется
локально; сетевых обращений Orange при этом нет. Контроллер завершает свой
subscriber при выходе/SIGTERM/SIGINT.

Чёрный кадр игры, пропажа HDMI-сигнала, открытие нашего меню и смена игры не
являются подтверждённым standby. Для сна используется системное состояние,
а не яркость изображения. После сброса UI получает OFF из локальных настроек;
его обновление не удерживает Orange активным.

Реализовано в пакете 0.1.7, проверено тестами на payload и переходах. На ТВ
подписка/реальные имена состояний ещё не проверены. Если API недоступен или не
подтверждает подписку, новая версия безопасно остаётся OFF; это нужно разрешить
по реальному ответу G5, не обходить автоматически проверку питания.

## 1. Получение свежего кадра

### 1.1. Кто управляет отправкой

**Единственный координатор кадров — постоянный контроллер OSD на ТВ.**
Это контроллер сессии, а не renderer букв или открытая страница меню.
Меню задаёт ручной ON/OFF; контроллер допускает задания. TV relay
исполняет его решение и передаёт кадр; самостоятельно вторую цепочку не запускает.
Orange запрашивает следующий кадр, когда готов, но не может обойти ручной OFF
или неподтверждённое бодрствование ТВ. OSD управляет жизнью сессии; Orange —
потребностью в новом кадре. TV берёт кадр только по запросу Orange и после допуска.
PicCap продолжает обычный видеозахват независимо от перевода.

| Участник | Ответственность |
| --- | --- |
| Контроллер OSD | Разрешить/остановить сессию, проверить питание и один запрос свежего кадра |
| PicCap / TV relay | Только по допущенному запросу Orange взять кадр, упаковать и отправить один раз |
| Orange OCR | После готовности запросить кадр, завершить detector/кропы и запросить следующий |
| База / переводчик | Обработать версии текста независимо от следующего кадра |
| Renderer OSD | Показать только актуальный допустимый результат |

Состояния координатора: `STOPPED`, `READY`, `IN_FLIGHT`, `RECOVERING`.
`READY` здесь внутреннее состояние, не отдельный обязательный сетевой ответ.
В `READY` и при действующей сессии выдаётся ровно одно разрешение; перед
упаковкой состояние становится `IN_FLIGHT`. Оно сохраняется при упаковке,
передаче, detector и обработке кропов. Освобождение происходит только после
`OCR_DONE` того же задания/сессии, **не после detector и не после перевода**.
Свободный один из трёх NPU-работников не является разрешением на новый полный кадр.

Следующий кадр берётся свежим после освобождения, а не из очереди упаковок.
Нет FIFO кадров, догоняющих пропущенные моменты, и нет обязательных отправок
по секундному таймеру во время занятости Orange. Каждый принятый свежий кадр
продолжает проверку треков/TYPEWRITER/трёх наблюдений; готовый перевод или OCR-кэш
сам по себе не останавливает наблюдение за экраном.

На выключении перевода или смене источника разрешения прекращаются, epoch
сессии меняется. Уже выполняющийся OCR может завершиться, но его поздний
`OCR_DONE` не разрешает работу новой сессии, а ответ не попадает в её OSD.
При сетевом таймауте нельзя считать Orange свободным: переходим в `RECOVERING`,
проверяем состояние прежнего задания и готовность worker, затем разрешаем
**новый свежий** кадр. Не повторяем старый пакет как новое наблюдение.
Orange также должен отклонять занятую работу без постановки кадров в очередь.

Нужны идентификаторы сессии и задания, подтверждение OCR без ожидания переводов,
а также диагностика: состояние, возраст кадра, последний запрос/`OCR_DONE`,
число отправленных/отклонённых кадров, OCR-время и задержка до следующего кадра.
При исчерпанном Google-бюджете OCR/поиск кэша продолжаются при ручном ON;
запрещаются новые сетевые переводы, а не автоматически вся кадровая цепочка.

**Граница реализации:** это закреплённый контракт обновления. Текущий
`overlay/runtime-control.js` управляет допуском сессии, но отдельного кадрового
разрешения пока не выдаёт. `gocr_worker/tv_server.py` обрабатывает запросы
последовательно. В подготовленном live PP-OCR пути 0.1.8 OCR уже возвращается
без ожидания перевода; legacy/benchmark `frame_pipeline.py` сохраняет прежний
синхронный путь. Нужно ещё связать запрос Orange с выбранным кадром PicCap.
Сам пакет пока не установлен на ТВ. См. [двухэтапный путь](live-two-stage-translation.md).
Запрос кадров со стороны Orange и взятие кадра только после такого запроса
также являются следующим этапом; текущий transport всё ещё принимает кадр от TV.

### 1.2. Свежесть и частота

При ручном ON и активном режиме координатор разрешает новый
захват после завершения обработки текущего кадра.
ТВ берёт свежий RGB-кадр PicCap 1280×720, упаковывает его в LZ4 и отправляет на
Orange. Не готовим пакеты непрерывно заранее и не накапливаем старые кадры.

Частоту задаёт координатор OSD по результату завершённого OCR:

- **Пустой экран:** успешный `OCR_DONE` сообщает ноль текстовых областей.
  Следующий свежий кадр запрашивается не раньше чем через 1000 мс от начала
  предыдущей отправки и только после завершения OCR.
- **Текст найден:** следующий свежий кадр запрашивается сразу после завершения
  OCR, без дополнительной секундной паузы. Проверки TYPEWRITER и стабильности
  продолжаются по готовности обработки.
- **Ошибка или таймаут:** это не пустой экран и не подтверждение готовности.
  Действует `RECOVERING`, описанный выше; секундный таймер не разрешает отправку.

Для пустого экрана координатор вычисляет:

```text
next_request_at = max(previous_send_started_at + 1000 ms, ocr_done_at)
```

Оба времени измеряются монотонными часами координатора на ТВ. Время захвата
в пакете сохраняется отдельно для проверки свежести; сравнивать часы ТВ с
часами Orange для этого таймера не нужно. OCR сообщает результат и завершение,
а не командует «подожди секунду»: оставшееся время вычисляет OSD.

Например, отправка началась в 0 мс, пустой OCR завершился в 200 мс — остаётся
800 мс ожидания. Если он завершился в 1300 мс, новый свежий кадр запрашивается
сразу, без ещё одной секунды. Истечение таймера во время работы Orange не
создаёт новое задание. До разрешения не готовим и не накапливаем LZ4-пакеты.

Наличие только имён/непереводимых подписей, расход Google-бюджета или отсутствие
ответа переводчика **не** равны нулю текстовых областей. Ручной OFF,
смена сессии имеют приоритет над разрешением по таймеру.
Если текст появился после пустого кадра, он будет обнаружен на следующем
разрешённом OCR-проходе; пустой режим добавляет до секунды ожидания запроса,
кроме времени упаковки/передачи/обработки и возможного восстановления связи.

Переводчики не должны задерживать следующий кадр. Обычный видеозахват PicCap
остаётся отдельным процессом со своей частотой; OCR получает выбранные свежие
кадры. Это правило пока является контрактом обновления, а не установленным
на ТВ изменением scheduler.

Пакет содержит номер и время захвата. Повтор одного пакета не считается новым
наблюдением. Новый реальный захват неизменившегося изображения является новым
наблюдением, даже если пиксели совпадают.

## 2. Detector и треки областей

Orange выполняет detector и существующее формирование кропов/склеенных блоков.
Каждая область получает независимый трек. В нём хранятся:

- геометрия и принадлежность строк блоку;
- текущий исходный текст, его версия и число совпадений;
- состояние NEW / TYPEWRITER / VERIFY / STABLE / CHANGED / DISAPPEARED;
- время последнего признака изменения;
- идентичность сессии и выбранный язык перевода;
- ожидающие задания и результаты переводчиков;
- состояние отображения OSD.

Сравниваем одну область между кадрами, а не разные кропы разных участков экрана.
Используем существующее геометрическое сопоставление; небольшое дрожание границ
не должно создавать новую реплику. Геометрические допуски требуется проверить
на реальных кадрах, а не назначать произвольно.

## 3. Признаки TYPEWRITER

Рост кропа является одним из признаков печати, а не самостоятельным доказательством
готовности или неготовности текста. Наблюдаем:

- расширение области вправо/вниз;
- появление новой строки;
- дописывание распознанного текста с сохранением предыдущего текста как начала.

Detector может сразу выделить область полного размера. Поэтому отсутствие роста
геометрии само по себе не означает окончания печати. Рост из-за дрожания detector,
движение панели и реальная смена реплики должны различаться трекером.

Пока TYPEWRITER уверенно установлен, пропускаем обычное распознавание этой
области и не отправляем её в переводчики. Detector/трекер продолжают наблюдения;
остальные области кадра обрабатываются нормально.

Каждый новый признак печати обновляет время последнего изменения. Большое число
одинаковых быстрых кадров не снимает TYPEWRITER автоматически.

После паузы без замеченных изменений переходим в VERIFY и выполняем контрольный
OCR. Если текст продолжает расти — возвращаем TYPEWRITER. При фиксированном bbox
этот контроль необходим: без OCR мы не видим дописывание внутри неизменной области.

Порог паузы ещё не выбран. Обсуждался начальный диапазон 300–500 мс и учёт
наблюдаемого интервала печати в игре. Это кандидаты для теста, не production-константы.
Длинная пауза внутри печати всё равно возможна; проверка актуальности позднего
перевода остаётся обязательной.

## 4. Очередь OCR

Сначала идут склеенные многострочные блоки, затем крупные кропы. Три постоянных
работника с отдельными RKNN-контекстами берут задания из общей очереди.
Один кроп не выдаётся двум работникам.

Перед NPU проверяем общий точный кэш OCR: модель/режим/размер/все grayscale-пиксели.
SHA-256 служит индексом, совпадение дополнительно проверяется по полным байтам.
Изменённый кроп распознаётся заново. Одинаковые одновременно ожидающие запросы
используют один результат. Пустые ответы и ошибки не сохраняем как готовый текст.

Кэш не меняет идентификатор захвата и не создаёт искусственных подтверждений.
Если точные пиксели нового реального кадра совпали, его сохранённый OCR-результат
может участвовать в наблюдении без повторного NPU Invoke.

Блок готов только после получения всех его исходных строк. Собираем целую
реплику; очередь выполнения не меняет порядок строк и координаты результата.

## 5. Подтверждение готового текста

После проверки окончания TYPEWRITER нужны три последовательных свежих наблюдения
с одинаковым исходным текстом. Совпадения увеличивают счётчик, не создают повторный
перевод. Изменение создаёт новую версию и сбрасывает подтверждения. Дописывание
возвращает TYPEWRITER.

Для сравнения текста сохраняем регистр, пунктуацию и символы. Допустима явная
версионированная нормализация Unicode/пробелов; нельзя склеивать разные реплики
удалением знаков или приблизительным сравнением.

Google не получает недописанный/неподтверждённый текст: сначала подтверждаем
окончание печати и три совпадения. До этого Bergamot может дать предварительный
перевод допустимой завершившей печать версии блока. Совпадения считаются по
исходному тексту одной области в трёх свежих кадрах, не по трём разным работникам
или совпадению русского перевода. Изменение исходного текста сбрасывает допуск
Google для предыдущей версии. Это сокращает расход символов внешнего API.

Ошибка/пустое распознавание не является подтверждением. Конкретное правило
обработки одиночных ошибок и подтверждения исчезновения ещё требуется выбрать,
чтобы не возвращать известное мерцание OSD.

## 6. Допуск текста при ручном ON

Автоматически язык не определяем. Применяем существующий допуск: реплики/описания и подтверждённые заголовки
панелей; имена, неподходящие подписи, кнопки и сомнительный OCR не переводим.

Для русского экрана пользователь выключает перевод вручную. Это не снимает
проверку качества OCR, TYPEWRITER или правила допуска текста. Режим «все области»
по-прежнему позволяет также короткие названия и подписи, сохраняя качество OCR.

## 7. База и Google Cloud Translation API

Решение пользователя: в целевой цепочке **Google Cloud Translation - Basic v2,
стандартный NMT, авторизация API key** заменяет окончательный MADLAD в выбранном
Google-режиме. **Bergamot остаётся первым предварительным этапом.** Используем
официальный API, а не Google Lens, браузерную сессию или неофициальный endpoint.
В проекте уже есть `_translate_google` в `translator/server.py`; при реализации
расширяем этот путь, не создаём второй клиент Google.

Для подтверждённой разрешённой реплики проверяем постоянную базу с полным
ключом: нормализация, языки, тип текста, переводчик, версия модели, исходный текст/хэш.
После совпадения хэша сравниваем нормализованный исходный текст.

Есть перевод **Google** — используем его без API-запроса и расхода месячного
лимита. Нет — проверяем бюджет, резервируем символы и отправляем текст Google.
При промахе Google-кэша допустимую версию сначала отдаём Bergamot и показываем
актуальный предварительный результат. Google вызывается после этого этапа и
только когда та же исходная версия получила три последовательных подтверждения.
Bergamot и Google работают над целыми блоками; кадры не ждут этих переводов.
Предварительный Bergamot не записывается в постоянный кэш Google.
Старые записи MADLAD сохраняем отдельно: не выдаём их за Google и не используем
автоматически при смене провайдера. Исходный и переведённый тексты сохраняются.

Разные целые реплики независимых областей могут переводиться параллельно.
Бюджет у них общий, поэтому проверка и резервирование должны быть атомарными.
Не разбиваем реплику по каждой точке ради параллелизма: сохраняем смысл и
проверенную обработку иконок/имён. Если она создаёт несколько HTTP-запросов,
каждый фактически отправляемый текст проходит отдельный бюджетный допуск.

Одинаковые запросы с одинаковыми параметрами объединяем между областями и кадрами.
Один перевод используется в нескольких треках, но их геометрия, подтверждения и
отображение остаются независимыми. Для каждого трека хранится только последняя
актуальная ожидающая версия, а не очередь всех промежуточных обрывков.

### 7.1. Жёсткий месячный предел: 490 000 символов

Пользователь не разрешает платное превышение. Предел проекта — **490 000
символов за расчётный месяц**, с запасом 10 000 относительно опубликованного
бесплатного объёма Google NMT. На дату проверки Google описывает первые
500 000 символов как ежемесячный кредит $10, общий для Basic/Advanced;
неиспользованный кредит не переносится. Считаются Unicode code points исходного
текста, включая пробелы и непереводимые символы, а не байты UTF-8 или слова.
Источник: [тарификация Google](https://cloud.google.com/products/translate/pricing).

Точный расход нашего запроса вычисляем по окончательному значению `q` перед
HTTP-отправкой, включая маркеры и пунктуацию. Это правило подходит также для
японского и китайского текста. Пустые запросы запрещаем. API detect-language
отдельно не вызываем: язык определяет существующая локальная логика.

Счётчик и журнал запросов храним **постоянно на Orange в БД**, не в оперативной
памяти ТВ. Перезапуск, смена HDMI/игры, очистка кэша или ротация ключа не обнуляют
расход. Все работники и клиенты этого бюджета используют один журнал.

Перед каждой отправкой в одной транзакции:

1. Проверяем актуальность реплики и кэш; одинаковое ожидающее задание объединяем.
2. Считаем символы реального запроса.
3. Проверяем `учтённые_символы + активные_резервы + новый_запрос <= 490000`.
4. Записываем резерв, идентификатор попытки и расчётный период; только после
   успешного сохранения разрешаем сетевой запрос.

При успехе резерв становится учтённым расходом. При таймауте, потере связи или
сбое после возможной отправки сохраняем его как консервативный расход: нельзя
считать, что Google ничего не обработал. Каждая повторная сетевая попытка требует
нового резерва. Освобождать резерв можно лишь если доказано, что отправки не было.
Незавершённые попытки после перезапуска также не возвращают бюджет автоматически.
Недоступная/повреждённая БД или неопределённый период запрещают новые запросы.

Запрос, который пересечёт границу, **не отправляем целиком**. Не обрезаем
предложение ради остатка. В состоянии `GOOGLE_MONTHLY_LIMIT` продолжают работать
OCR, поиск готовых переводов Google в базе и OSD для этих записей. Новые реплики
без кэша не отправляются Google. Уже включённый предварительный Bergamot может
продолжать локальный этап; его результат отмечается как предварительный и не
выдаётся за ответ Google. MADLAD и платное превышение автоматически не включаются.
Меню показывает расход, доступный остаток, причину остановки
и следующий подтверждённый период сброса.

Сброс происходит только после подтверждения нового расчётного месяца Google,
по времени сервера, а не по часам телефона/ТВ. Границу периода и timezone нужно
проверить перед включением реального ключа; суточный reset квот Google не доказывает
границу месячного кредита. При неопределённости оставляем API заблокированным.

### 7.2. Защита ключа и границы гарантии

Ключ хранится только на сервере в AES-256-GCM vault; мастер-ключ и приватная
директория имеют owner-only права. Ввод на ТВ идёт через loopback с последующим
RSA-OAEP шифрованием до передачи Orange. На HTTP-странице телефона ввод закрыт;
secure-context ввод использует WebCrypto. В Git, URL QR-кода, ответы браузеру/OSD
и журнал ключ не попадает. Все запросы
на перевод проходят через серверный бюджетный допуск, а не напрямую с телефона/ТВ.

Реализованный счётчик показывает календарный месяц UTC и дополнительно ограничивает
расход за скользящие 32 дня: `490000-max(monthly, rolling32days)`. Поэтому на границе
месяца полный бюджет не восстанавливается автоматически; защитное окно не зависит
от недоказанного timezone Google. Меню показывает расход и остаток каждые 3 секунды.
Точное поведение и пределы гарантии: [Google budget / OSD](google-budget-osd.md).

Перед включением проверяем право на месячный кредит и прочее использование
Cloud Translation, которое может расходовать тот же кредит. У нового API key
не появляется самостоятельных бесплатных 500 000 символов. Выделенный проект,
ограничения API key и серверные квоты служат дополнительной защитой; нельзя
обещать отсутствие платежей по одному локальному счётчику, если тот же кредит
или ключ используется другими приложениями вне нашего журнала.

Документация Google описывает дневные/минутные квоты; дневной объём по умолчанию
не ограничен. Они не заменяют наш месячный стоп. Источник:
[квоты Google](https://docs.cloud.google.com/translate/quotas).
Уведомление о расходе также не заменяет запрет отправки.

## 8. Завершение перевода

Google возвращает окончательный результат после предварительного Bergamot.
Если тексты переводов совпали, OSD не обновляем. Если отличаются — обновляем
актуальную область окончательным Google-ответом. Сохраняем исходный и
переведённый тексты, провайдера/версию, языки и статистику использования записи.
Ошибка, пустой ответ или отказ по бюджету не становятся записью перевода.

Перед показом проверяем актуальность трека и версии исходного текста:

- тот же перевод уже показан — не перерисовываем его;
- новый готовый перевод актуальной реплики — передаём в OSD;
- устаревший трек/текст — результат не обновляет экран;

Устаревшее ещё не начатое задание отменяем. Уже выполняющийся перевод может
закончиться и заполнить базу для будущего повторения; это не разрешает показ
устаревшего результата сейчас.

## 9. OSD

Готовые области обновляются независимо. Короткая реплика не ждёт генерации
другой длинной области. Перевод сохраняется, пока оригинал остаётся на экране.
Подтверждённое исчезновение/смена оригинала обновляет его трек.

Для перехода между самостоятельными репликами сохраняем минимум пять секунд
чтения и очередь следующего текста. Обновление предварительного Bergamot
окончательным Google для той же версии не является новой репликой в очереди;
оно применяется только при отличающемся переводе и действующем треке.

Дописывание текущей реплики не создаёт очередь промежуточных переводов. Вся эта
логика должна учитывать отдельные области, а не один общий глобальный текст.

## 10. Языковая автоматика отменена

После последнего упрощения нет `rus+eng`, начального `LANGUAGE_CHECK`,
`RUSSIAN_IDLE`, периодических пятиминутных проверок языка или чёрного перехода
как языкового триггера. Пользователь сам включает перевод для иностранной игры
и выключает его для русского меню/игры. Прежние обсуждения доступны в истории Git,
но не являются текущей спецификацией.

Ограничение PP-OCRv6 small остаётся: его установленный label map не содержит
русских букв. Ручной ON на русском экране не делает его распознавание правильным;
необходимость остановить перевод в этом случае решает пользователь.

- установка меню/контроллера 0.1.8 и физическая проверка tvpower, пульта,
  standby/wake и тишины Orange на OFF;
- возможная глобальная горячая кнопка поверх HDMI — отдельное исследование.

### Уточнения после проверки ручной цепочки

Проверены исходники текущего full-frame пути, а не работа нового пакета на ТВ.

1. **В live relay 0.1.8 выбранный переводчик подключён из session.**
   Provider/host/port зафиксированы для задания; изменение инвалидирует старую
   публикацию. Legacy/benchmark путь ещё использует CLI translator по прежнему контракту.
2. **Фоновые обращения на OFF устранены в пакете 0.1.6, ожидается установка.**

   задание может завершиться по новому правилу; показывать его ответ после OFF
   нельзя. Сетевая тишина не является доказательством отмены принятого запроса Google.
3. **В 0.1.8 счётчик live пути перенесён до final HTTP.** Три свежих равных
   исходных наблюдения допускают Google после предварительного Bergamot.

4. **В 0.1.8 убран casefold из идентичности трека.** Регистр/пунктуация теперь

5. **Прежний ON больше не восстанавливается в версии 0.1.7.** Старт контроллера,

## Дополнение 0.1.9: предварительный перевод по предложениям

Bergamot получает завершённые предложения до `.`, `!`, `?`; сокращения и
многоточия не являются самостоятельной границей. Готовые предложения
переиспользуются при дописывании блока и добавляются в OSD по порядку. Хвост
ждёт завершения; для строк без пунктуации пока сохранены три подтверждения.
Финальный переводчик получает целую реплику после трёх совпадений.

OSD начинает с левого верхнего края области, сохраняет якорь продолжающейся
реплики и уменьшает размер только при нехватке места. Изменение размера
анимируется 180 мс; переносы строк пересчитываются сразу. Это не заменяет
будущий TYPEWRITER detector и не доказывает завершение печати. Ограничение

OSD и переключатель — одно приложение «Перевод игры». Иконка открывает большой
тумблер по центру, настройки находятся внутри отдельного раздела этого же меню.
«Назад» скрывает меню, сохраняя OSD поверх игры. Отдельный settings app удалён.
Ручной ON/OFF, сброс после sleep/wake и телефонное управление сохранены.
Установка и доказательства: [unified-osd-app.md](unified-osd-app.md).
